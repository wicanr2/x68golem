# 020 — 256 色模式下，第 0 頁的 word 只有低 byte 是真的

日期：2026-09-06

## 症狀

畫地圖的迴圈是

```
0x070C82  10 18     move.b (a0)+,d0     ← 來源 byte 進 d0 的低 byte
0x070C84  34 C0     move.w d0,(a2)+     ← 整個低 word 寫進 0xC00000
```

而 `d0` 的高位留著前一行 `_B_SUPER` 的回傳值（呼叫者的 USP，`0x0009C8xx`）。
所以每一個 word 都是 `0xC8yy`。我們照著寫進去，圖形平面就填滿了
137,600 個 `0xC7`／`0xC8` 高位元組——**MAME 在同一刻高位元組全部是 0**。

## 量到的

在 MAME 上讀視訊控制器的暫存器：

```
CRTC R20(0xE80028)=0x0115  視訊 R0(0xE82400)=0x0001
```

視訊控制器 R0 的色數欄位 = 1 ＝ **256 色**（0 是 16 色、3 是 65536 色）。
同一刻第 1 頁（`0xC80000` 起 4096 bytes）也是全 0。

## 結論

X68000 把同一塊 512 KB 的 VRAM **依色數對到不同的位址視窗**：

| 色數 | 頁 | 視窗 | 一個 word 裡有效的位元 |
|---|---|---|---|
| 16 色 | 4 頁 | `0xC00000`／`0xC80000`／`0xD00000`／`0xD80000` | 低 4 bit |
| 256 色 | 2 頁 | `0xC00000`／`0xC80000` | 低 8 bit |
| 65536 色 | 1 頁 | `0xC00000` | 全部 16 bit |

**256 色模式下寫進第 0 頁視窗的高 byte 收不到**——那半個 word 不存在，
讀回來是 0。這不是「我們把它遮掉比較好看」，是硬體如此，
而 `move.w d0,(a2)+` 這種「低 byte 才是像素、高位是垃圾」的寫法
在真機上一直都能用，正是因為硬體會丟掉。

實作在 `internal/x68k/bus.go` 的 `Bus.GraphicsBPP`：
`_CRTMOD` 設模式時填（`GraphicsBPPForMode`，目前只有量過的模式 8 → 8），
`WriteWord`／`WriteByte` 在第 0 頁視窗把高 byte 丟掉。

## 這一份要留下來的規則

**「暫存器裡的垃圾會被硬體丟掉」是一個真的機制，不是巧合。**
看到程式把明顯是垃圾的高位一起寫進周邊時，先問「那些位元在真機上存在嗎」，
不要先假設程式碼有 bug 或自己的模擬要照單全收。
