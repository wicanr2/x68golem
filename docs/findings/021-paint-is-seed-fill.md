# 021 — `_PAINT` 是種子填充，不是邊界填充

日期：2026-09-06

## 症狀

圖形平面在最後一鍵之後整片變成 0。`_PAINT` 的紀錄說明了為什麼：

```
_PAINT (174,117) 色 0x8C → 塗了 262144 個像素
_PAINT (173,143) 色 0xDC → 塗了 262144 個像素
…
_PAINT (167,196) 色 0x00 → 塗了 262144 個像素   ← 最後這一次把整面洗成 0
```

**每一次呼叫都塗滿整個 512×512。**

## 原因

第一版照「邊界色＝填色」做邊界填充：把所有**不是 fill**的相連像素塗成 fill，
碰到 fill 才停。地圖上的州界是各種顏色的線，沒有一條是 fill 那個顏色，
所以填充永遠停不下來。

正確的語意是**種子填充**：記下起點的顏色，把「與起點同色」且相連的像素
塗成 fill，碰到任何別的顏色就停。

## 驗證

改成種子填充之後，27 次呼叫各塗 398–1,937 個像素，加起來 23,251：

```
_PAINT (174,117) 色 0x8C 起點色 0xFF → 塗了 887 個像素（掃描線段 66、堆疊最深 443）
_PAINT (37,197)  色 0xBF 起點色 0xFF → 塗了 1937 個像素（掃描線段 119、堆疊最深 904）
_PAINT (167,196) 色 0x00 起點色 0xDE → 塗了 32 個像素（掃描線段 12、堆疊最深 13）
```

圖形平面的非 0 像素從 0 變成 96,201——與 MAME **完全相同的數字**。

## 順帶排除掉的一個假設

真機的 `_PAINT` 在作業區不夠時會中途放棄，所以「作業區上限」看起來像是
剩餘差異的候選解釋。把每一次呼叫用掉的掃描線段與堆疊深度印出來之後，
那個假設被排除：出問題的那一次（50 段、深 165）是全部 27 次裡**最小的幾個之一**，
而更大的（119 段、深 904）都對得上。**不是資源上限。**

剩下的差異另有原因，見 `docs/findings/022` 的結尾。

## 這一份要留下來的規則

平台手冊上的一句話（「塗滿被指定色圍住的區域」）可以同時符合兩種實作，
而那兩種在真實資料上差了三個數量級。**手冊挑不出來的，資料挑得出來**——
「每次都塗滿整個畫面」這個數字一秒就把錯的那個判掉了。
所以 `_PAINT` 這種帶語意的服務要印出**它做了多少事**，不只是「有沒有回錯」。
