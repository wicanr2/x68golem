# 005 — 亂數不在遊戲裡：`sub_60580(n) == rand() % n`，而 `rand()` 在 `FLOAT2.X`

日期：2026-09-06

這是目前最有價值的一項：**這個專案的核心功能（控制亂數）找到掛點了，
而且掛點不在遊戲的位址上，在機器層的服務邊界。**

## 怎麼找到的

`$FE0D`／`$FE0E` 是映像裡僅有的兩個高可信度 FLOAT2 呼叫
（`cmd/probe -scan-float`：字對齊掃描出 97 種號碼，但**只有這兩個後面
緊接著 `rts`**——其餘 95 種是位元組樣式落在分支位移與資料裡的假陽性，
與 IDA 對 `trap #15` 掃描時 289 個候選只有 28 個是真的，是同一種現象）。

兩個都是三行小函式：

```
0x06F28A  FE0E              rts          ← 沒有參數
0x06F28E  move.l (4,sp),d0  FE0D  rts    ← 一個 long 參數
```

找誰呼叫它們（`cmd/probe -find`）：

| 包裝 | 呼叫站點 |
|---|---|
| `$FE0D` | `0x06A184`、`0x06A2C2`、`0x06AB48`（三處，都在初始化） |
| `$FE0E` | **`0x06058E`** ——一處 |

`0x06058E` 落在 `sub_60580` 裡面。那正是
`sangokushi_x68k_cht` 的 `docs/spec/02` 記的「原版亂數 `sub_60580(n)` 回 0..n−1」。

## `sub_60580` 全文

```
0x60580  2F02        move.l d2,-(sp)
0x60582  242F 0008   move.l (8,sp),d2        ; d2 = n
0x60586  4A82        tst.l  d2
0x60588  6604        bne.s  0x6058E
0x6058A  7000        moveq  #0,d0            ; n == 0 → 回 0
0x6058C  600E        bra.s  0x6059C
0x6058E  4EB9 0006F28A  jsr $6F28A           ; ← rand()
0x60594  2202        move.l d2,d1
0x60596  4EB9 0006ED4A  jsr $6ED4A           ; 長整數取餘
0x6059C  241F        move.l (sp)+,d2
0x6059E  4E75        rts
```

**`sub_60580(n) == rand() % n`。** 那個 `rand()` 是 `FLOAT2.X` 提供的
F-line 服務——`CONFIG.SYS` 載的驅動（`docs/findings/004`），
**不在 `SANMAIN.Z` 裡面**。

實跑也對得上：開機時看到 `srand(1308)` 一次（`$FE0D`，參數 `0x51C`），
接著 `rand()` 被呼叫 200 次。

## 為什麼這個掛點比較好

掛在 `$FE0E` 是**機器層的服務邊界**，不是遊戲的某個位址：

- 換一個 X68000 程式一樣成立（分層沒有破，`docs/spec/006`）。
- 不必假設遊戲的函式位址，也不會因為版本不同而失效。
- 攔截點與 `_SETBLOCK`、`_OPEN` 走的是同一條路，不需要另一套機制。

## 現在能做什麼

`cmd/probe -rand-fixed 12345` 已經可以讓整個開機流程跑在受控的亂數上，
200 次取值全部由我們決定。模式見 `internal/x68k/rng.go`：
`Fixed`／`Seq`／`Replay`，序列用完就**報錯而不是退回真亂數**。

## 為什麼沒有「直通」模式

直通要能重現 `FLOAT2.X` 的 `rand()` **逐位元相同**，而那個演算法還沒解出來
（它在磁碟上的 `FLOAT2.X` 裡）。在解出來之前，**任何「大概對」的亂數都比
停下來糟**：它會產生自洽但錯的對拍結論，而那正是這個專案要消滅的東西。

所以 `RNGUnset` 是預設，碰到 `rand()` 就 fail-closed。
解 `FLOAT2.X` 的 `rand()` 是接下來的一項獨立工作；解出來之後
`sangokushi_x68k_cht` 那邊也能把自己的 `Rand` 介面對上原版的序列。
