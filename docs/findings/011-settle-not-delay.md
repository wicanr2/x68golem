# 011 — 固定延遲送按鍵是不可靠的

日期：2026-09-06

## 症狀

把 `-key-delay` 從 20,000,000 週期調到 6,000,000 之後，同一串按鍵跑出來的
畫面變成

```
何名でプレイしますか (0-8)? 5
プレーヤー 3. は どの英雄を選びますか (1-8)?
```

`5` 是要給「Computerの強さ」的，卻落進了「何名でプレイしますか」。
從那一刻起整串序列錯位，後面每一鍵都對到錯的提示。

## 為什麼

**畫面要畫多久不由我們決定。** 每個提示前面的處理時間差很多——
讀檔、清畫面、畫八個君主的表格，各自要的週期數不一樣。固定延遲只有
兩種結局：等太短就錯位，等太長就一次跑幾十分鐘。

## 改法：等真的訊號

`Oracle.WaitSettled(settle, max)` 跑到「連續 settle 個週期沒有人寫
text VRAM」為止。

判準用「有沒有人寫 VRAM」而不是「畫面雜湊有沒有變」：

- 前者是**真的訊號**——畫面在動就一定有人寫。
- 後者要每隔幾步去雜湊 128 KB，貴，而且取樣之間的變化看不到。

`Bus` 因此多記兩個數字：最後一次寫 text VRAM 的週期、寫入次數。

`cmd/play` 用它跑序列，每按一鍵存一張圖——**序列走到哪裡看得見**，
不必事後從最後一張圖回推是哪一步歪掉的。

## 一般化

這條適用於任何「送輸入給互動程式」的自動化：

> 固定延遲是在猜對方要多久；等一個對方自己發出的訊號才是同步。

`sangokushi_x68k_cht` 那邊的 MAME 腳本目前仍用固定時間（`play.lua` 的
`t = 58.0` 那種），因為 MAME 的 Lua 沒有便宜的方式看 VRAM 寫入。
兩邊的做法不同這件事本身要記著：**對拍時如果只有一邊會錯位，
就會誤以為是模擬錯了。**
