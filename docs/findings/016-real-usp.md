# 016 — 真機的 USP 量到了：`0x0009C768`，我們是 `0x0009C810`

日期：2026-09-06

`docs/findings/015` 把圖形平面的高 byte 差異追到

```
0x070C7C  trap    #15        ← _B_SUPER(0)，回傳值進 d0
0x070C82  move.b  (a0)+,d0   ← 只動低 byte
0x070C84  move.w  d0,(a2)+   ← 卻寫整個 word
```

高 byte 是回傳值的 bits 8–15。要知道真機是多少，只有問真機。

## 量法

MAME 的 Lua 可以讀 CPU 暫存器（`cpu.state["USP"].value`）。在指令畫面
取樣一次：

```
command 暫存器：USP=0x0009C768 SR=0x00002600 D0=0x0000006C
                A0=0x00FF9DC8 A1=0x00000000 A2=0x0008640E
```

**真機 USP = `0x0009C768`；我們是 `0x0009C810`——差 `0xA8` ＝ 168 bytes。**

## 這解釋了什麼，沒解釋什麼

**沒解釋高 byte。** `0x0009C768` 的 bits 8–15 是 `0xC7`，而 MAME 的
VRAM 高 byte 全是 `0x00`。所以真機在那一段迴圈裡 d0 的高位不是 USP
——要嘛回傳值不是 USP，要嘛真機根本沒走那一段迴圈（我們走了）。
**兩種都還沒排除，不要挑一個寫進文件。**

**但它本身是一個要修的差異。** 168 bytes 的堆疊位置落差表示我們的
crt0 交棒／`_SETBLOCK` 之後的記憶體版面與真機不完全一樣。那個差異
會影響任何「把堆疊上的值寫進記憶體」的地方——這個遊戲已經被抓到
會這樣做一次了。

## 下一步（兩條，互相獨立）

1. 把 168 bytes 的落差找出來：比對我們與真機在 crt0 之後的記憶體版面。
   最便宜的做法是同一個手法——在 MAME 取樣幾個關鍵位址，與我們的比。
2. 確認真機到底有沒有執行 `0x070C82` 那個迴圈：在 MAME 取樣
   `0xC00000` 附近的寫入來源做不到（沒有 watchpoint），
   但可以比對兩邊的低 byte 圖案——如果低 byte 一致而只有高 byte 不同，
   那就是同一段迴圈；如果連圖案都不同，那是不同的路。

第 2 條現在就能做：低 byte 的相同率是 **63.30%**，不是接近 100%——
**所以兩邊多半不是同一段程式在畫**。這一條是目前最該追的線索。
