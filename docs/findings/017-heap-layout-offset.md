# 017 — 圖形平面對不上的根，是一個 168 bytes 的記憶體版面落差

> **後續**：記憶體版面的落差在 `019` 解掉（環境區塊長度），本篇對 `+0x30`／`+0x34` 的推測是**錯的**（`018` 已排除）。圖形平面最後對上的完整經過見 `019`–`022`。

日期：2026-09-06

追到底了。這一份把整條鏈寫下來，因為每一步都是量出來的。

## 1. 我們的 256 色平面**一個像素都沒畫**

改成 256 色之後（`docs/findings/015`），我們的低 byte 非 0 像素是 **0**，
MAME 是 **96,201**。「63.30% 相同」全部來自兩邊都是 0 的背景——
那個數字看起來像進度，其實是空的。

**這是一個假通過的形狀**：比對率不低，但它衡量的東西是空的。

## 2. 畫圖的迴圈讀到 0

`-hook 0x070C84` 印出攔截當下的暫存器：

```
攔截 0x070C84：D0=0x0009C800 D1=0x000001FF A0=0x000BBE93 A2=0x00C00000
```

```
0x070C82  move.b (a0)+,d0    ← 從 0x0BBE93 讀一個 byte
0x070C84  move.w d0,(a2)+    ← 寫進 0xC00000（VRAM）
```

`D0 = 0x0009C800`：低 byte 是 **0**，所以來源那個 byte 是 0。
高 byte `0xC8` 是 `_B_SUPER` 回傳值留下來的（`docs/findings/015`）。

## 3. 來源落在資料的**尾巴外面** 429 bytes

檔案讀進來的位置（`_READ` 的緩衝區位址）：

```
KOEI.PIC     12,800 bytes → 0x09951C
HEXGRP        3,072 bytes → 0x081160
MMAPGRP      47,336 bytes → 0x0A515A
SMAPGRP      46,136 bytes → 0x0B0A4E   （結束於 0x0BBCE6）
SANGOKU.PAL     512 bytes → 0x079F40
```

`0x0BBE93 − 0x0BBCE6 = 0x1AD = 429`。**來源指標指到 `SMAPGRP` 結束之後
429 bytes 的地方**，而那裡在我們的記憶體裡是 0。

## 4. 我們的堆疊比真機低 168 bytes

MAME 在同一個畫面取樣：**`USP = 0x0009C768`**；我們是 `0x0009C800`
（`docs/findings/016` 量到 `0x0009C810`，這一次的取樣點略有不同）。
落差是同一個量級的常數。

## 結論與下一步

**我們的堆積／堆疊版面與真機差一個常數**，於是每一份載入的資料都落在
稍微不同的位址，而依賴「資料是連著放的」那段程式就會讀到界外。

最可疑的地方已經標好了：`internal/human68k/process.go` 的
**`A0+0x30` 與 `A0+0x34`**。它們從一開始就標成 **L3**——
「意義未知，crt0 會讀」，我們兩個都填了「區塊結束位址」。
crt0 讀完就把它們搬到別處存起來，而**堆積的邊界很可能就是從那裡算的**。

要定它，得知道真機在那兩個欄位裡放什麼。做法與這一輪相同：
在 MAME 取樣那兩個 long。**這是一個明確、可量的下一步，不是猜。**

## 這一份要留下來的教訓

「比對率 63.30%」看起來像有一半對了，實際上是**兩邊都空**。
比對率要配上「非 0 的量」一起看——
`gvpng` 輸出的「非 0 像素 0」那一行才是真正戳破它的東西。
