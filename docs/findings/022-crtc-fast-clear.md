# 022 — 換畫面的清除是 CRTC 的高速クリア，不是 CPU 迴圈

日期：2026-09-06

## 症狀

種子填充修好之後（`docs/findings/021`），地圖畫對了，但畫面右上角與右緣
留著開場圖的殘影：我們 109,220 個非 0 像素，MAME 96,201，差 13,417。

殘影從**第一個畫面就在**，之後一次都沒被蓋掉：

```
gvram-00  非 0 203609   右上角區 6155   右緣條 4288
gvram-24  非 0 181586   右上角區 6155   右緣條 2456
```

而 MAME 在開場圖那一刻也是 **203,609**（與我們相同），到了下一個畫面
（雙龍）只剩 64,001。**真機把整面清掉了，我們沒有。**

## 清的人不是 CPU

在 MAME 上盯住幾個應該變成 0 的像素，同時每個 periodic tick 取樣 PC：

```
清畫面：t=65.69 探針非 0 由 4 變成 0，PC=0xFF9E1C
    t=65.42 PC=0xFF9E1C
    …（前 16 個取樣點全部在 0xFF9E1C 一帶，那是 IPL ROM 的按鍵掃描迴圈）
```

**512 KB 在兩個取樣點之間（16 ms 內）就清完了。** CPU 迴圈做不到：
262,144 個 word 至少要三百多萬個週期，10 MHz 下超過 0.3 秒，
會橫跨十幾個取樣點。所以清的人是硬體。

## 是哪一個硬體動作：從遊戲的程式碼讀出來（L0）

`0x070CEA` 那支常式收一個頁遮罩當參數：

```
0x070CEA  4CEF 0002 0004  movem.l (4,sp),d1        ← 頁遮罩
0x070CF0  7081            moveq  #-127,d0
0x070CF8  4E4F            trap   #15               ← _B_SUPER
0x070CFC  0239 00F0 …2B   andi.b #$F0,($E8002B).l  ← R21 低 4 位清掉
0x070D04  E209            lsr.b  #1,d1
0x070D06  6400 000A       bcc.w  →0x070D12
0x070D0A  0039 0003 …2B   ori.b  #$03,($E8002B).l  ← 第 0、1 頁
0x070D12  E209            lsr.b  #1,d1
0x070D18  0039 000C …2B   ori.b  #$0C,($E8002B).l  ← 第 2、3 頁
0x070D20  41F9 00E8 0481  lea    ($E80481).l,a0
0x070D26  0010 0002       ori.b  #2,(a0)           ← 動作：開始
0x070D2A  0810 0001 67FA  btst/beq                 ← 等硬體收到
0x070D30  0810 0001 66FA  btst/bne                 ← 等硬體做完
```

**收頁遮罩、把它攤進 R21 的低 4 位、對動作埠設 bit 1、等它自己清掉**——
那是**高速クリア**。先前 `internal/x68k/crtc.go` 把 bit 1 註記成
「ラスタコピー」，那是沒有證據的假設；現在有證據了。

頁與位址的對應接上 `docs/findings/020`：256 色模式下 16 色的四頁兩兩合成
一頁，所以 bit0／bit1 都指第 0 頁（`0xC00000`），bit2／bit3 都指第 1 頁
（`0xC80000`）。遊戲清的正是第 0 頁。

實作在 `internal/x68k/bus.go` 的 `fastClearGraphics`。

## 結果：圖形平面與真機逐位元組相同

同一段按鍵序列，五個取樣點：

| 畫面 | MAME 非 0 像素 | 我們 | 相同 |
|---|---|---|---|
| 開場圖 | 203,609 | 203,609 | **100.00%** |
| 雙龍（劇本選單） | 64,001 | 64,001 | **100.00%** |
| 君主資料 | 24,710 | 24,710 | **100.00%** |
| 君主資料（第二次取樣） | 24,710 | 24,710 | **100.00%** |
| 指令畫面（地圖）| 96,201 | 96,201 | 99.85% |

指令畫面差 **398 個像素**，全部集中在一塊 30×24 的州：MAME 是 `0xFF`（白），
我們是 `0x73`。對得上 `_PAINT (201,169) 色 0x73 → 塗了 398 個像素` 那一次。

**那不是繪圖差異，是遊戲狀態差異。** 我們那一次跑在 `-rand-fixed 12345`，
MAME 跑的是原版的亂數。把亂數換成直通（載入真的 `FLOAT2.X`，
`docs/findings/014`）再跑同一段序列：

```
低 byte 相同 262144/262144 = 100.0000%
MAME 非 0 96201 我們非 0 96201
```

**逐位元組相同。** 那一州的歸屬本來就會隨亂數不同，
控制亂數之後兩者的差異就從「畫面對不上」變成「說得出是哪一次亂數」——
這正是這個專案存在的理由（README §為什麼不用 MAME）。

## 這一份要留下來的規則

**「這個清除快得不像 CPU 做的」是一個可以量的判準。**
遇到「狀態突然整批改變、但找不到寫入者」時，先算一次
「如果是 CPU 迴圈要跑多久」，再拿取樣頻率去比。
量級對不上就別再找程式碼裡的迴圈了，去找硬體動作。

另一條：`docs/findings/017`／`018` 花了兩輪從「畫圖迴圈讀到 0」往回猜，
猜錯兩次；`019` 改成「先量出常數（兩份資料差同一個值），再找誰產生那個常數」，
一次就中。**先量差值再找原因，比從症狀往回猜便宜。**
