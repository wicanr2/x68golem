# 015 — 圖形平面對 MAME：63.30%，而差異的原因是一個沒被初始化的暫存器

日期：2026-09-06

M3 的圖形面第一次有數字了。方法與文字面相同（`docs/findings/009`）：
MAME 那邊 dump `0xC00000` 起的 512 KB，兩邊走同一條序列到指令畫面。

## 訂正一：不是「16 色四頁」，是 **256 色**

第一版照「一個 word 放四頁、每頁 4 bit」重建圖形平面。對出來的結果是
我們的第 2、3 頁各有 137,600 個非 0 像素，**而 MAME 是 0**。

攤開 MAME 的 dump 就知道為什麼：

- 高 byte **永遠是 0**（只有一種值）；
- 低 byte 有 **55 種**值，包含 255／191／128／113／105 這些**大於 15** 的。

所以一個像素是**低 byte 的 8-bit 調色盤索引**。遊戲用 `_CRTMOD 8`。
**這是量出來的，不是查表**——手上沒有可信的 `_CRTMOD` 模式表，
而 dump 自己就把答案講清楚了。

改成 256 色之後：**索引相同 165,943／262,144 ＝ 63.30%**。

## 訂正二：剩下的差異來自一個沒被初始化的暫存器

我們還有 137,600 個像素的**高 byte 非 0**，值只有兩種：`0xC7` 與 `0xC8`。
`-watch 0xC00000` 指出寫的人：

```
0x070C7A  moveq   #$81,d0
0x070C7C  trap    #15          ← _B_SUPER(0)，回傳值進 d0
0x070C7E  movea.l d0,a1
0x070C80  move.w  d3,d1
0x070C82  move.b  (a0)+,d0     ← 只動 d0 的低 byte
0x070C84  move.w  d0,(a2)+     ← 卻寫整個 word 進 VRAM
0x070C86  dbf     d1,-6
```

`move.b` 只設低 8 bit，`move.w` 寫 16 bit——**高 byte 是 `_B_SUPER` 回傳值
的 bits 8–15 留下來的**。我們回的是舊 USP `0x0009C810`，
bits 8–15 = `0xC8`，於是每個像素的高 byte 都是 `0xC8`。

MAME 那邊高 byte 全是 0 ⇒ **真機上那一次呼叫的回傳值，bits 8–15 是 0x00**。

## 這一項的意義

遊戲把**沒有初始化的暫存器位元寫進 VRAM**。它在真機上無害（高 byte 在
256 色模式下不顯示），但對拍時它是一個**逐位元的指紋**：
要讓 VRAM 逐位元相同，`_B_SUPER` 的回傳值就得與真機相同，
不能只是「功能上正確」。

**不猜一個能讓像素對上的回傳值。** 那正是會產生自洽但錯的結論的做法：
改對了畫面、改錯了語意，而下一個依賴 `_B_SUPER` 回傳值的地方就會歪。
要定它，得先知道真機在那一刻的 USP 是多少——那是下一步。
