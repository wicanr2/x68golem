# 018 — 真機的程式管理區塊：兩個 L3 欄位定下來了

日期：2026-09-06

`.Z` 是固定位址載入（基底 `0x4FFFA`），所以真機上的管理區塊也在
`0x4FEFA`。在 MAME 上把那 0x40 bytes 印出來：

```
+00=00049ED0  +04=00040100  +08=000FCA86  +0C=00000000
+10=00049CD0  +14=000419E2  +18=0006E9AE  +1C=0006E9AE
+20=00045F0E  +24=1F000000  +28=00000000  +2C=00000000
+30=0008A9B6  +34=0008A9B6  +38=0008B874  +3C=00047C9A
路徑 = "A:\"   檔名 = "SANMAIN.z"
```

對照 `sangokushi_x68k_cht` 的 `docs/re/01` 的段界
（text `0x4FFFA–0x715B2`、data `0x715B2–0x8A9B6`、bss `–0x8B874`）：

| 欄位 | 值 | 是什麼 |
|---|---|---|
| `+0x08` | `0x000FCA86` | 這一塊記憶體的結束 |
| **`+0x30`** | **`0x0008A9B6`** | **data 段結束（＝ bss 起點）** |
| **`+0x34`** | **`0x0008A9B6`** | 同上（crt0 兩個都讀）|
| **`+0x38`** | **`0x0008B874`** | **bss 結束** |

`+0x30`／`+0x34` 先前標 L3「意義未知」，我們兩個都填了「區塊結束位址」
（`docs/findings/017` 把它們列為最可疑的未知數）。**現在是量出來的。**

順帶兩件小事：檔名是 **`SANMAIN.z`（小寫 z）**，不是我們填的大寫；
`+0x08` 是 `0x000FCA86` ≈ 1 MB，不是我們預設的 2 MB 減去 supervisor 堆疊。
兩者都已經可以設定。

## 但這**不是**圖形平面對不上的原因

把 `+0x30`／`+0x34`／`+0x38` 改成量到的值、把 `+0x08` 設成 `0xFCA86`，
**執行過程一道指令都沒變**（兩次都是 80,721,278 道），畫圖迴圈的來源
指標還是 `0x000BBE93`。

**所以那條假設被排除了。** 記下來比改對了更重要——
`docs/findings/017` 推測「堆積邊界從那兩個欄位算」，那個推測是錯的。

## 剩下的線索

畫圖迴圈一次寫 512 個像素（`d1 = 0x1FF`），來源每列 512 bytes，
整個畫面要 256 KB。來源起點 `0x0BBE93`，往上 256 KB 是 `0x0FBE93`
——**很接近真機的區塊結束 `0x0FCA86`**。所以那是一塊佔住記憶體頂端的
大緩衝區，而它的內容是**遊戲自己組出來的**（讀進來的檔案總共才 ~100 KB）。

我們那塊緩衝區是空的。下一個要量的東西很明確：
**MAME 在 `0x0BBE93` 那一帶有沒有資料**。

- 有 ⇒ 我們少做了「把地圖組進緩衝區」那一步，要去找是哪一段。
- 沒有 ⇒ 我們讀的位址本身就是錯的，要回頭追那個指標怎麼算出來的。

**兩種都還沒排除，所以不寫結論。**
