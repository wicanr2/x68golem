# 002 — CPU：MC68000

狀態：**READY**（2026-09-05）

## 1. 範圍

**只做 68000（MC68000／68EC000），不做 68010 以上。**

依據是普查而不是猜：`SANMAIN.Z` 的 669 個函式、36,934 道指令裡，
去掉尺寸後綴只有 **71 種指令**，68020 以上專屬 **0 種**，浮點 **0 種**
（`sangokushi_x68k_cht` 的 `docs/design/06` §4.1(a)）。

⚠ 那個數字只數 IDA 認成程式碼的部分，**是下界不是全部**。
所以實作範圍以「68000 完整指令集」為準，普查只用來說明工作量不是無底洞。

## 1.5 核心不是從零寫的

`m68k/` 是 [`atari-talos-ai-toolkit`](https://github.com/wicanr2/atari-talos-ai-toolkit)
的 `internal/m68k` **原封複製**（`m68k/PROVENANCE.md`）。Atari ST 與 X68000
都是 MC68000，這一層沒有平台差異，**不該有第二份實作**。

複製當天就在本專案跑過：**240,168 筆語料全部通過**（`tools/go.sh test ./m68k/`）。

代價是會分岔，所以 `tools/sync-m68k.sh --check` 存在——它讓分岔被看見，
而不是等到某一天兩邊的除以零行為不一樣才發現。修正一律回上游改。

## 2. 驗收判準：全部通過，不是大部分通過

語料是 [SingleStepTests/680x0](https://github.com/SingleStepTests/680x0) 的
68000 v1（硬體產生，不是別人的模擬器產生的）。

**CPU 的錯不會報錯**，只會讓上層在幾百萬個指令之後畫錯一個像素，
或讓某一場戰鬥的損失差 1。所以判準是每個 opcode 檔 100%，
不接受「99.8% 已經很好了」。

語料與手冊衝突時**以語料為準**，但要在 `docs/spec/` 寫清楚是從語料反推的、
手冊怎麼寫、哪一個檔幾筆資料支持。

## 3. 決定性

- **不讀主機時鐘、不讀主機亂數。** 時間只有一個來源：累計週期數。
- 未初始化的記憶體讀出固定值（`004` 訂），不是 Go map 的迭代順序。
- 同一顆種子、同一串輸入 ⇒ 同一條指令軌跡。這是**測得出來的**：
  `oracle` 的 `TestDeterminism` 跑兩次比 trace 雜湊。

## 3.5 已知缺口

| 指令 | 狀況 |
|---|---|
| `addx.l` | **未實作**（`m68k: opcode 0xd181 is not implemented`）。`SANMAIN.Z` 用到 1 次 |

核心對沒實作的 opcode 是 fail-closed 的，會指名 opcode 而不是安靜地當 NOP。
缺口以 `coverage/isa_gap_test.go` 追蹤——**不在 `m68k/` 裡加測試**，
那會讓 `sync-m68k.sh --check` 報分岔。補好之後那支測試會自己從 skip 變成 pass。

## 4. 未定（DRAFT）

- 週期數精度：先做「指令級」計數（每道指令的標稱週期），
  不做匯流排等待狀態。畫面時序真的對不上再升級。
- 例外處理的堆疊框格式：68000 的 group 0/1/2 各不同；先做 group 1/2
  （TRAP、除以 0、非法指令），bus error 的長框等有需要再補。
