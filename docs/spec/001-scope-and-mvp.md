# 001 — 範圍與 MVP

狀態：**READY**（2026-09-05）

## 這是什麼

**無頭、決定性、可以當 Go 套件 import 的 X68000 執行器**，為程式化觀測而寫。

第一個案例是 KOEI 1988 X68000 版《三國志》（`SANMAIN.Z`）與
[`sangokushi_x68k_cht`](https://github.com/wicanr2/sangokushi_x68k_cht) 的對拍，
但**目標不是只跑那一支**：分層與判準見 `006`。

姊妹專案 [`dosgolem`](https://github.com/wicanr2/dosgolem) 做同一件事，
平台是 x86 ＋ DOS。上面兩層（觀測、runtime）的契約刻意對齊，下面兩層全新。

## 為什麼不用 MAME

MAME 是對的參考實作，**這個專案不取代它**——`003` §驗收 把 MAME 當畫面 oracle。
但有三件事它給不了：

| | MAME 0.264（本專案量過）| x68golem |
|---|---|---|
| 攔截函式呼叫讀參數 | Lua 的 `debug:bpset` 是 function，**呼叫下去整個行程當場消失**（無錯誤訊息、`pcall` 接不到、三次重跑一致；`sangokushi_x68k_cht` 的 `docs/design/06` §4.6）| 語言層的 callback |
| 快照分支 | `x68000` driver 標 `savestate="unsupported"` | 記憶體結構直接複製 |
| **控制亂數** | **給不了。** 外掛只能觀測，不能決定 | `005` §4 |

第三項是這個專案存在的主要理由。對拍時「原版跟 remake 為什麼不一樣」
有兩個來源：規則不同，或亂數不同。**亂數不受控的時候，這兩個分不開**——
只能多跑幾場再談信賴區間。把亂數變成輸入，對拍就從統計推論變成逐項比對。

> 實例：`sangokushi_x68k_cht` 為了定出一斉攻撃的分攤除數，花了八輪去**製造**
> 一個包夾局面（一場 17 分鐘、三層樂透），最後還是靠「同一條亂數流、
> 不同常數」的交叉檢定才分得出 2 和 3。亂數可控的話，那是讀一次參數的事。

## MVP 的出口條件

**冷啟動 → 標題畫面 → 指令畫面，畫面與 MAME 的索引截圖逐點相同，
且同一顆種子跑兩次逐位元組相同。**

不在 MVP 裡：音源發聲、FDC 的低階時序、SCSI、MIDI、滑鼠。

## `[HARD]` 不散布原版素材

本儲存庫不含 `SANMAIN.Z`、磁碟映像、IPL ROM 或 CGROM。
需要原版的測試**缺檔就 skip**——安靜的替代品會讓「還沒做完」看起來像做完了。

CGROM 尤其不能內嵌：它是 Sharp 的。字模在對拍時**由原版自己從 CGROM 取**，
使用者自備；remake 那邊則自建字庫（那是 remake 的事，不是這裡的事）。
